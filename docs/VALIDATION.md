# Validation and deployment boundaries

Application 0.1.1 packages the returned Microsoft-signed private kernel driver 0.1.0.0. The signed INF matches the submission and the SYS Authenticode-protected content matches the qualified unsigned candidate. Microsoft catalog trust and INF/SYS membership were verified. The returned package passed isolated Windows 10 x64 live-installation campaigns normally and under standard Driver Verifier; neither signing nor bounded tests certify all Windows/storage configurations.

The public native build uses C++17, static CRT, W4/WX, CFG, ASLR and NX. Offline protocol tests check wire sizes, bounded lengths, timestamps, duplicate IDs and one million deterministic malformed completion records. User-mode AddressSanitizer is a separate configuration. The exact shared private kernel ring is tested for two million deterministic push/drain iterations and overwrite ordering, normally and with AddressSanitizer.

The private KMDF driver builds with W4/WX, PREfast and CFG. InfVerif Windows/Universal checks and catalog generation are required before a submission CAB is prepared. The kernel protocol contains no pointers. One SYSTEM/administrator handle owns the control device. Event buffering is fixed-capacity, and collection is inactive without an owner-started recording.

The first attachment policy accepts only the explicitly selected, present, unpartitioned 64 MiB Titan Storage Fault Lab synthetic disk. The SDK verifies its exact adapter hardware ID/service and opened-handle vendor/product/serial, capacity and sector size. Physical disks, storage-pool members, other virtual disks and the Windows disk are inventory-only or refused targets. Disk class-wide filters, automatic PnP restarts and host installations are outside the test plan. Existing per-device filters are preserved; detected concurrent edits stop the operation rather than being overwritten. Detach remains available after partitioning. A control-interface resource/name failure does not fail the disk's AddDevice; close old recorder handles and restart the selected scratch device/Windows if diagnostic publication needs to be retried. Read and write requests are timed; flush and other operations are forwarded without a timing record.

Completed live validation used an owned synthetic 64 MiB RAM-backed Storport disk in an isolated Windows 10 x64 Hyper-V guest. The validator checked the disk's exact ancestor, opened-handle vendor/product/serial, capacity, sector size, disk number and PDO binding before generating test data. It never targeted a physical drive. It exercised real 4 KiB writes/reads, unchanged payload/completion semantics, metadata timing, 600 overflow writes, 1,024 concurrent transfers, queue drain, owner cleanup and an owner-open PnP restart. The completed signed-package campaigns are recorded below.

Remaining qualification includes Windows 11, Secure Boot/HVCI, representative physical adapters, storage/security filter coexistence, power transitions, installation rollback and long-duration high-queue-depth workloads. No guarantee of zero defects, vulnerabilities, data loss or overhead is made. Do not deploy the preview to valuable or system media.

The dispatch/completion QPC interval is at this filter boundary. It cannot attribute latency to individual downstream drivers, establish physical media timing or reconstruct application/end-to-end latency. Completed requests may appear out of sequence; overwritten metadata is explicitly counted. The viewer never measures hardware latency by drawing synthetic graphs.

## Completed final-candidate VM campaigns

The final unsigned submission image was exercised with a temporary guest-only test signature on Windows 10 build 19045 x64, normally and under standard Driver Verifier targeted at both storage components. The actual Storport disk was detected by Windows; no physical drive was targeted or formatted. The fault lab passed deterministic error/recovery tests, 1,024 concurrent transfers, malformed controls/SCSI bounds, restricted-token access checks, a real adapter bus reset and abrupt-owner-exit lease expiry. The recorder passed data/status integrity, completion metadata, 600 overflow writes, 1,024 concurrent transfers, owner cleanup and a PnP restart with its control owner still open. Filter association was removed without changing unrelated entries; both drivers unloaded. Both VM baselines and all nine historical checkpoints were preserved; no new minidump was observed.

These are bounded VM qualification results, not Microsoft-signed return-package tests or Windows 11, Secure Boot/HVCI, physical-controller, power-transition, storage coexistence or long-duration qualification. The original unsigned package is the CAB submission; guest certificates and signed lab copies stay private. Initial failed startup experiments and corrections remain in private evidence.


## Signed distribution checks

- Both self-contained setup executables compile with the same strict native build settings. Their embedded INF, CAT and SYS resources exactly match the verified Microsoft return; resource checks load files as data without executing either installer on the host.
- The signed application's two CTest cases pass: bounded protocol/duration validation, one million deterministic malformed-record cases, and 20 installer identity/signature checks. The same tests pass in a separate user-mode AddressSanitizer build. Identity tests include raw DIR13 validation, absolute/traversal/nested/wrong-directory rejection, duplicate directives and UTF-16LE INF handling.
- Seven additional read-only checks exercise the installer policy against the actual returned INF and Microsoft catalog, then confirm refusal of an altered catalog. No disk, registry association or installation is changed by those checks.
- The complete recorder archive includes the separately signed Fault Lab UI and console setup executables. The driver source and guest lab certificates stay private; no loose unsigned driver is a public installation method.
- The actual signed console setups passed installation, per-device attachment, detachment and complete removal in the isolated Windows 10 campaigns below. The installed SYS images matched the verified Microsoft return exactly.

The signed-installation campaign found that SetupAPI expands the same canonical `%13%` service-binary directive differently when reading a source or published primitive INF. The installer validates the bounded raw canonical directive instead of comparing that environment-dependent expansion. Its other product-identity checks, Microsoft-root catalog policy and INF/SYS membership checks remain required; an arbitrary absolute service path is not accepted.

## Completed Microsoft-signed package campaigns

On 2026-10-25, both production-signed storage packages passed an isolated Windows 10 build 19045 x64 campaign, then the same campaign with standard Driver Verifier targeted at both drivers. Test signing was disabled and no guest test certificate or host security change was used. The actual self-contained console setups installed the packages, attached the recorder to the selected synthetic disk, detached it after the requested normal restart and completely uninstalled both packages. Existing unrelated disk filters were preserved.

In each campaign, the recorder passed its 83-check runtime suite and 88-check owner-open restart suite, including 1,024 concurrent transfers and 600 overflow writes. Restricted-token control access was refused. The accompanying Fault Lab completed its deterministic error/recovery and concurrent-transfer tests. The installed published INF and DriverStore INF passed the product-identity check while the Microsoft catalog and INF/SYS memberships remained valid. No new minidump was observed; the VM returned to its original powered-off baseline and all nine historical checkpoints were preserved.

These are bounded synthetic-disk VM results. They do not establish physical-media performance, a hardware-latency benchmark, Windows 11/Secure Boot/HVCI compatibility or production suitability for valuable disks. The UI installer shares the exercised setup core and its embedded package was verified as data; the console installer performed the live installation operations.
